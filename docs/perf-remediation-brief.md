# /z/ 性能整改简报（立项输入）

> 2026-10-08。用户实测结论：「通了，但性能极差，几乎无法使用」；决定后续立项整改。
> 本文档汇总截至立项时已观察到的事实、候选根因与测量计划，作为整改项目的输入。
> 关联截图：用户会话 Quick test message（/z/ 实测，含回复重复渲染的缺陷）。

## 症状

1. 整体卡顿，「几乎无法使用」（用户原话，2026-10-08）。
2. **正确性缺陷（同源）**：同一条 assistant 回复在时间线里渲染两遍（用户截图可见）。

## 已观察到的证据（均为实测）

| # | 证据 | 含义 |
|---|---|---|
| E1 | 引擎本机 loopback 流量 **28.8MB / 6s**（85 条并发连接，`ss -tni` 两次采样差分） | 有东西在持续搬运大 payload，量级远超正常 UI 会话 |
| E2 | 桥接层热路径：每个会话事件 → 400ms 去抖 → **全量**重取 `/api/session/:id?limit=200` → 全量重建 rows → `JSON.stringify` 全量对比 → 增量或全量快照（`zcodeAgentService.liveUpdate`） | O(N) 每事件；会话越长越糟；大会话必然劣化 |
| E3 | 行号 = 在扁平列表里的**位置序号**（buildRows 从 1 顺序编号） | 中间插入一行（流式中 assistant 块增长、工具行后新出文本行）会使**后续所有行 rowId 位移** → diff 把它们当「删+增」→ 疑似重复渲染的机制（与症状 2 同源） |
| E4 | 工具卡富渲染按 messageId 回取 `/api/session/:id/message/:msgId`（5s TTL 缓存），每次 rebuild 都会对未命中项重查 | 工具多的会话在流式期间反复回查 |
| E5 | `providerSettingsService.getView` 每次调 2 个端点（配置摘要 + /api/models）；设置页/引导反复调用（观测到数秒内 6 次） | 请求风暴的一部分 |
| E6 | 快照帧携带**全部** rows（seq = rows.length），无窗口化 | 大会话每次快照都是全量传输 |

## 候选根因（待测量确认）

1. **热路径全量重建 + 全量对比**（E2/E3）：整改方向 = 行身份改为**内容寻址**（card/part id），
   diff 改为按键对比；快照只发尾部窗口（ZCode 协议本有 rowsWindow/游标分页，未用满）。
2. **事件扇出无合流**（E1）：引擎 `/api/event` 对每个订阅者重复推送完整 payload；多订阅者
   （ocrc host 镜像 + UI）时流量成倍。整改方向 = ocrc 侧合流/去重，或推动引擎侧节流。
3. **重复渲染缺陷**（症状 2）：与 1 同源，行身份稳定后应一并消失；整改时以回归测试钉住。

## 测量计划（立项后第一步）

- 隔离栈回放大会话（构造 200/500/1000 行三档），CDP Tracing/Profiler 分「网络 / 脚本 / 渲染」计时。
- 指标：首屏时间、单事件处理耗时（P50/P95）、内存、loopback 字节速率。
- 每项整改以「不回退既有指标 + 单事件处理 < 16ms（不掉帧）」为验收线。

## 测量结果（N9-0 基线，2026-10-09 隔离栈实测）

环境：隔离栈 4199（adopt 4298 引擎，big-pickle/ling-3.0-flash-fin-free）；基线会话 = 真实驱动 90+ 回合，**206 卡**（≈410 行级）；CDP headless 2200×1200、Network cache disabled。指标 = fetch 包装器（页面内 performance.now 计时 + body 字节）+ PerformanceObserver longtask + 服务端 ocrc.log 时间戳差分。两次独立长回合复测。

| 指标 | 实测值 | 备注 |
|---|---|---|
| 首屏（导航 → 首行渲染） | **1.27–1.54s** | 目标 <2s@200 行：✅ 当前达标（虚拟化列表 DOM 只挂可见窗口） |
| 单次 history refetch（`limit=200`,206 卡） | 服务端 **12–122ms**（中位 ~30ms），页面侧 avg 30–31ms / max 40–72ms | 每次 ~46–52KB |
| liveUpdate 触发节奏 | 去抖后 **~1000ms 一次**（实测 gaps 999/1005/997…）；turn 开始有一次 ~2s 窗 | 400ms 去抖 × 事件流合流后的实际节律 |
| 单回合 refetch 次数 | 15 次 / 15.5s 回合（长文本回合）；9 次 / 12s | 每次都是全量 46–52KB → 单回合 ~0.7MB loopback |
| longtask（主线程 ≥50ms） | **1 次/回合，50–148ms** | 全量重建+stringify 落在主线程的直接证据；<16ms 验收线现状不达标 |
| 服务端 24h 日志全量统计（含多页签调试混流） | 181 次 refetch / 2min 窗口，gap 中位 31ms、min 1ms | 多订阅者会成倍放大（对应 E1/E6） |
| 重复渲染 | 本轮 90 回合压测未复现用户截图的两遍渲染 | 但机制（E3 位置 rowId）仍在代码里，需 N9-1 根除+回归测试钉住 |

**结论**：首屏达标；瓶颈集中在 ①liveUpdate 全量 refetch+全量重建+双重 stringify（longtask 50–148ms,主线程掉帧）②每事件全量快照的字节放大（~50KB×每去抖窗）。N9-1/2/3 按计划执行。

## 整改后复核（N9-5，2026-10-09 隔离栈实测）

同一隔离栈、216 卡会话（N9-4 E2E 的 fork 子会话）、同一测量方法：

| 指标 | 基线（206 卡） | N9 后（216 卡） | 验收线 |
|---|---|---|---|
| 首屏 | 1.27–1.54s | **1.84s** | <2s ✅ |
| 单回合 refetch 次数 | 15 次/15.5s | **8 次/5.6s**（250ms 去抖 + diff 空不发） | — |
| 页面侧单次 refetch | avg 30–31 / max 40–72ms | avg 49 / max 100ms（服务端 24–49ms,会话更大） | — |
| 流式期重复行（DOM rowId 去重采样） | 机制仍在代码里未复现 | **11 次采样全部 0,定稿 0** | 无重复行 ✅（内容寻址根除） |
| longtask/回合 | 1 次 50–148ms | 1 次 137ms | <16ms ❌ 未达标——全量 rebuild O(N) 是残余瓶颈,窗口化（动 vendor 语义）按计划不做,留观察 |
| sdelta | 无（host 未接线） | **每回合 9+ 帧,250ms 批次** | ✅ |

结论：三条硬验收线（首屏 <2s、无重复行、sdelta 复活）全过；单事件 <16ms 依赖全量重建本身,refetch 次数已减半,如仍不可接受需立项窗口化（rowsWindow 游标协议已在,属独立改动）。

## 边界

- 整改期间**冻结**会话面热路径上的新功能（附件、分享等走既有通道，不得加深全量重建）。
- 引擎侧问题（E1 的扇出）若需上游配合，单独立项，不阻塞 ocrc 侧整改。
