# 三发现优化方案：同步补齐 + 长会话窗口化 + question 交互问询（双端）

## 探索结论（现状依据）

- **发现①对症点**：CardBus 环形 buffer 只有 100 条、丢最旧无上报（card-bus.ts:48-52）；ws-hub 重放后发 `replayEnd` 但客户端是空操作（ws-hub.ts:69、+layout.svelte:130）；客户端 `upsertCard` 无 seq 缺口检测（sessions.ts:44-46）；重连只靠 100 条重放，断线期间超过 100 卡即**静默残缺**。这正是 sse-lagged 解决的问题，我们的修法更简单：TCP 保证在线不丢帧，缺口只发生在"断线窗口 > buffer"，所以**服务端显式上报"重放不完整"+ 客户端 REST 重同步**即可，无需心跳级滞后检测。
- **发现②对症点**：feed 全量 `{#each}` 渲染（+page.svelte:188-194），历史端点只回最后 50 条 message 且无 offset（history.ts:79、session.ts:7-14）；活跃会话 feed 无界增长（曾发生 569 卡冻结浏览器）。messageToCards 每条 message 恰产 0/1 卡，按 message 偏移分页语义干净。
- **发现③证据**：OpenAPI 快照核实 V1 三端点（`GET /question?directory=`、`POST /question/{id}/reply` body `{answers: string[][]}`、`POST /question/{id}/reject`）+ 三事件（`question.asked/replied/rejected`，properties 含 id/sessionID/questions[]）；V1 SDK 无 question 符号 → 照 skills/worktree 先例 raw fetch；**TG 侧 QuestionManager + interaction-manager question 槽位 + 中文 i18n 已全部移植但零接线**（question-manager.ts:7-244）；web 侧零命中，照 approval 卡片全链路模板（CardApproval → POST /api/approval → resolvePermission）。

## 实施批次（每阶段 tsc 0 错误 + 双 vitest 套件绿 + web build 过才 commit）

### 阶段 A：Web 同步补齐可靠性（借鉴 sse-lagged）——最小，先做

**A1 服务端**
- `card-bus.ts`：新增 `oldestSeq(sessionId): number | undefined`（buf[0]?.seq，空 buffer 返回 undefined）；`DEFAULT_BUFFER` 100 → 256（pruneFeeds 本就只驻留当前会话，内存无虞）。
- `ws-hub.ts` subscribe 分支：计算 `complete = since === 0 || (oldest === undefined ? since >= currentSeq : since >= oldest)`；`replayEnd` 增加 `complete` 字段。

**A2 客户端（web）**
- `+layout.svelte`：`replayEnd` 处理从空操作改为——`complete === false` 时执行 `resyncViaRest()`：`api.history(id)` → `setHistory` → 用新 lastSeq 重新 subscribe（resyncInFlight 闩防抖）。
- `+layout.svelte` onCard 增加缺口安全网：`card.seq > feed.lastSeq + 1` 时去抖 500ms 触发同一 `resyncViaRest()`。
- `notify.ts` visibilitychange 保持现状（TCP 在线不丢帧，无需再加）。

**A3 测试**：card-bus oldestSeq、ws-hub complete 标志三态（since=0 / 落 buffer 内 / 落 buffer 前）、store 重同步动作、upsertCard 缺口触发。

### 阶段 B：长会话窗口化渲染

**B1 服务端分页**
- `backend.ts`：`getHistory(id, limit?, offset?)` 加第三可选参。
- `opencode-backend.ts`：取全量 messages 后按 `messages.slice(-(limit+offset), len-offset)` 开窗再转卡（cardsFromMessages 支持窗口参数）；`acp-backend.ts` 忽略 offset（本就无界）。
- `routes/session.ts`：解析 `?offset=`（clamp 0..2000），响应增加 `hasMore`（cards.length >= 本次请求 limit 的启发式）。

**B2 前端窗口化**
- `sessions.ts`：新增 `prependHistory(sessionId, cards)`（按 id 去重后前插，不触碰 lastSeq——历史卡无 seq）。
- `+page.svelte`：`visibleCount` 默认 80、切会话重置；渲染 `cards.slice(-visibleCount)`；顶部"加载更早"chip——本地还有未显示的卡就直接扩窗，否则 `api.history(id, {offset})` 取更早并 prepend；按钮在 `!hasMore` 后隐藏。
- 滚动锚定：prepend 后 `scrollTop = newScrollHeight - oldScrollHeight + oldScrollTop`（tick 后执行），不打断阅读位置；"跳到最新"按钮保留不动。
- `api/client.ts`：`history(id, opts?: {limit?, offset?})`。

**B3 测试**：session 路由 offset clamp 与 hasMore、prependHistory 去重、组件测试（窗口切片 + 按钮 + 锚定不回底）。

### 阶段 C：question 交互问询（TG + web 双端）

**C1 backend**
- `backend.ts`：可选方法 `listQuestions?(directory?)` / `answerQuestion?(sessionId, requestId, answers: string[][])` / `rejectQuestion?(sessionId, requestId)` + `capabilities.questions?: boolean`。
- `opencode-backend.ts` raw fetch 实现（照 worktree 姿势）：reply/reject 前先 `GET /session/{sessionId}` 解析 directory（OC Manager 已验证的作用域姿势），再 POST `/question/{requestID}/reply?directory=` body `{answers}`；404 QuestionNotFoundError 返回结构化"已失效"结果（双端据此提示"该问题已在其他界面回答"）。
- capabilities `questions: true`（opencode）；v2/acp 缺省 → UI 自动隐藏。

**C2 事件接线**
- `entry.ts` dispatchEvent 增三分支：`question.asked` → TG `handlePluginQuestionEvent` + cardBus.publish `{kind:'question'}` 卡；`question.replied/rejected` → 同 id 卡更新 resolved 态 + TG 清理。
- `v2/event-map.ts`：`question.v2.asked/replied/rejected` 映射为 V1 形状（防 V2 宿主丢事件）。

**C3 TG**（大头已预制，只做接线）
- `index.ts`：`handlePluginQuestionEvent`——asked 时把 `properties.questions` 适配成 `types/question.ts` 的 Question[]，经 interaction-manager question 槽位走 QuestionManager.startQuestions（多题/多选/自定义输入全支持）；槽位被权限占用时只发提示文本不排队（v1 简化）；提交收集 `string[][]` → `backend.answerQuestion`；外部 replied/rejected → dropWaitingQuestion + editMessageText"已在其他界面回答"。
- requestID→pending Map + 30 分钟 TTL 清扫（照 approvalTokens 先例）。

**C4 Web**
- `structured-card.ts`：kind `'question'` `{sessionId, requestId, questions, resolved?}`。
- `routes/question.ts`：POST `/api/question/reply|reject`（照 approval.ts 的 body 校验 + `reg.forSession().answerQuestion()`）；server.ts 注册。
- `client.ts` + `CardQuestion.svelte`：每题选项 chips（multiple 支持多选、custom 支持文本输入），提交/拒绝按钮，resolved 后变只读态；Card.svelte 分发注册；capabilities store 加 `questions` 门控。
- 不做独立 HUD/横幅（approval 同款 feed 卡已够用，scope 控制）。

**C5 测试**：backend fetch 三方法（fake fetch 含 404 分支）、路由、QuestionManager 接线（fake bot DI seam）、CardQuestion 组件。

### 收尾
- `scripts/spike-restart.sh` 重启一次 → 活体冒烟：①`/api/session/:id?offset=80` 验证 hasMore；②长会话（ses_f1ce1aab8ffe…）开 web 验窗口化与"加载更早"；③question E2E：TG 发"用 question 工具问我两个问题"，验证 TG 向导作答回传 opencode + web 同步出现卡片并可作答。
- 文档：parity-audit 附录补三节；command-data-plane-research 补 /question 端点段；记忆更新。

## 风险与回滚
- 阶段间完全独立、各自 commit，可单独 revert；A/B 纯 web 可靠性与性能，C 涉及新 backend 面（capability 门控，其他 backend 自动缺省）。
- question 端点目录作用域是踩过坑的点（OC Manager 特意先查 session 再带 directory），实现内聚在 backend，404 已答场景双端显式兜底。
- 红线不变：只动 spike 实例（4099/4598 隔离环境），不碰生产 octg。

## 交付物
Web 弱网/长断线自愈（buffer 256 + complete 上报 + REST 重同步）、长会话窗口化（80 卡窗 + 服务端 offset 分页 + 滚动锚定）、question 双端交互（TG 向导 + web 卡片，含外部已答同步）。预估 A 0.5d / B 1d / C 2d。
