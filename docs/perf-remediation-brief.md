# /z/ 性能整改简报（立项输入）

> 2026-10-08。用户实测结论：「通了，但性能极差，几乎无法使用」；决定后续立项整改。
> 本文档汇总截至立项时已观察到的事实、候选根因与测量计划，作为整改项目的输入。
> 关联截图：用户会话 Quick test message（/z/ 实测，含回复重复渲染的缺陷）。

## 症状

1. 整体卡顿，「几乎无法使用」（用户原话，2026-10-08）。
2. **正确性缺陷（同源）**：同一条 assistant 回复在时间线里渲染两遍（用户截图可见）。

## 已观察到的证据（均为实测）

| # | 证据 | 含义 |
|---|---|---|
| E1 | 引擎本机 loopback 流量 **28.8MB / 6s**（85 条并发连接，`ss -tni` 两次采样差分） | 有东西在持续搬运大 payload，量级远超正常 UI 会话 |
| E2 | 桥接层热路径：每个会话事件 → 400ms 去抖 → **全量**重取 `/api/session/:id?limit=200` → 全量重建 rows → `JSON.stringify` 全量对比 → 增量或全量快照（`zcodeAgentService.liveUpdate`） | O(N) 每事件；会话越长越糟；大会话必然劣化 |
| E3 | 行号 = 在扁平列表里的**位置序号**（buildRows 从 1 顺序编号） | 中间插入一行（流式中 assistant 块增长、工具行后新出文本行）会使**后续所有行 rowId 位移** → diff 把它们当「删+增」→ 疑似重复渲染的机制（与症状 2 同源） |
| E4 | 工具卡富渲染按 messageId 回取 `/api/session/:id/message/:msgId`（5s TTL 缓存），每次 rebuild 都会对未命中项重查 | 工具多的会话在流式期间反复回查 |
| E5 | `providerSettingsService.getView` 每次调 2 个端点（配置摘要 + /api/models）；设置页/引导反复调用（观测到数秒内 6 次） | 请求风暴的一部分 |
| E6 | 快照帧携带**全部** rows（seq = rows.length），无窗口化 | 大会话每次快照都是全量传输 |

## 候选根因（待测量确认）

1. **热路径全量重建 + 全量对比**（E2/E3）：整改方向 = 行身份改为**内容寻址**（card/part id），
   diff 改为按键对比；快照只发尾部窗口（ZCode 协议本有 rowsWindow/游标分页，未用满）。
2. **事件扇出无合流**（E1）：引擎 `/api/event` 对每个订阅者重复推送完整 payload；多订阅者
   （ocrc host 镜像 + UI）时流量成倍。整改方向 = ocrc 侧合流/去重，或推动引擎侧节流。
3. **重复渲染缺陷**（症状 2）：与 1 同源，行身份稳定后应一并消失；整改时以回归测试钉住。

## 测量计划（立项后第一步）

- 隔离栈回放大会话（构造 200/500/1000 行三档），CDP Tracing/Profiler 分「网络 / 脚本 / 渲染」计时。
- 指标：首屏时间、单事件处理耗时（P50/P95）、内存、loopback 字节速率。
- 每项整改以「不回退既有指标 + 单事件处理 < 16ms（不掉帧）」为验收线。

## 边界

- 整改期间**冻结**会话面热路径上的新功能（附件、分享等走既有通道，不得加深全量重建）。
- 引擎侧问题（E1 的扇出）若需上游配合，单独立项，不阻塞 ocrc 侧整改。
